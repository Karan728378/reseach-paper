## 2. Architectural Verification of Live Execution Loop

### 2.1 The Agent Runner (`execute_live_trial`)
In `protocol_v3_runner.py`, the live execution path is encapsulated in `execute_live_trial(...)`:
- **Driver Framework:** `browser-use==0.13.10` with Playwright chromium backend.
- **Vision Flag:** Explicitly forced to `use_vision=False` across all arms (ABS, ARIA, DATA-CFG, VIS) to ensure strict observation pipeline comparability and prevent uncontrolled multimodal token consumption.
- **Browser Context Isolation:** Each trial creates a fresh `BrowserSession` / Chromium incognito context with local storage, cookie, and cache clearing (`SessionManager.reset()`).
- **Safety Gate:** Governed by `SAFETY_GATE_UNLOCKED = False` as default-deny in code and enforced via CLI flags `--i-understand-this-will-charge-my-api-key`. Any invocation without the explicit toggle raises an immediate `RuntimeError("SAFETY GATE ACTIVE")` before browser instantiation or LLM dispatch.

### 2.2 Initial-State Seeding & Pre-Flight Validation
- Before navigation, the application state is deterministically initialized via direct HTTP endpoint or localStorage seeding.
- **Task T5 Assertion:** Precondition verification checks `localStorage.getItem('cart')` to assert exactly 1 item (`prod-1002`, Wireless Noise-Canceling Headphones, quantity 1) is present before the agent starts. If absent, the trial terminates immediately as `PRECONDITION_FAILED`.
- **Cart/Auth Clearing:** Tasks T1–T4 and T6 verify an empty cart state (`cart: []`) prior to trial start.

### 2.3 Step, Time, and Loop Limits
- **Max Steps:** Capped at 15 steps per trial. If `agent.step_count >= max_steps`, the agent terminates with `termination_reason: MAX_STEPS_REACHED`.
- **Timeout:** Per-trial timeout enforced via `asyncio.wait_for(trial_future, timeout=180.0)` (3 minutes). Unfinished sessions terminate with `termination_reason: TIMEOUT`.
- **Loop Stagnation:** Monitored by `browser_use` loop detection (`repetition=0, stagnation=5`) and custom action hash matching.

## 3. Observation & Prompt Interception Boundary

### 3.1 Prompt Interception Mechanism
To satisfy auditability without relying on third-party proxy logging, the runner intercepts model prompts at the `MessageManager` / Chat completion boundary:
- When a step is executed, the `SystemPrompt` + serialized DOM string + history are extracted.
- The outbound payload is recorded in the run log under `raw_prompt_history`.
- In offline mode, the mock chat model captures the exact inputs passed to `invoke()`.

### 3.2 Limitations of Local Interception
- **Provider-Side Preprocessing:** Intercepted prompts record the exact payload generated by `browser_use` before transmission over HTTPS. Any server-side tokenization adjustments, system prompt injection by Google AI / Anthropic endpoints, or cached prefix compression occur downstream on the provider infrastructure and cannot be verified locally.
- **Sanitization:** Prompts and responses logged to disk are stripped of any prospective environment variable credentials or API tokens.
